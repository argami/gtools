# team-lead

Orchestrate multi-developer task execution using Claude Code's Agent Teams. Spawns Developer-A, Developer-B, and a Reviewer agent, assigns tasks from a structured plan, manages parallel work via git worktrees, and enforces a rebase-only, linear-history workflow with ff-only merges.

**Prerequisite**: Your Claude Code session must have Agent Teams enabled:
```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude --teammate-mode auto
```

## Quick Start

```bash
/gtools:team-lead /path/to/tasks.md
```

The skill will:
1. **Resolve parameters**: read the tasks file, set up git worktrees (default), create a progress checkpoint
2. **Spawn teammates**: Developer-A, Developer-B, Reviewer (persistent for the session)
3. **Assign tasks**: send the first eligible task to the appropriate developer
4. **Wait for TASK DONE**: developers complete work, run tests, rebase, and report back
5. **Review & merge**: Reviewer approves or requests changes; Lead merges approved tasks into main
6. **Loop**: assign next eligible task, repeat until all done
7. **Cleanup**: remove worktrees, report completion

## Usage

### Basic (default: with worktrees)
```bash
/gtools:team-lead tasks.md
```
Creates persistent git worktrees at `<project>-worktrees/dev-a` and `<project>-worktrees/dev-b`. Developers work in parallel without stepping on each other's checked-out branches.

### Without worktrees (shared checkout)
```bash
/gtools:team-lead tasks.md no-worktrees
```
Developer-A and Developer-B share the project's working directory. Only one can have a branch checked out at a time — slower and more serialized, but uses less disk.

## Input: tasks.md Format

The skill reads a `tasks.md` file (typically generated by `/clavix:plan`) with this structure:

```markdown
# Implementation Plan

## Phase 1 — Foundation (sequential)

### Task 1: Set up database schema
**Owner**: Developer-A
**Spec**: 
- Create PostgreSQL migrations for users, posts, comments tables
- Add indexes on foreign keys
- Test: `pytest tests/db/` must pass green

### Task 2: Implement authentication
**Owner**: Developer-A
**Depends on**: Task 1
**Spec**:
- Add JWT-based auth endpoint
- Store hashed passwords
- Test: `pytest tests/auth/` must pass green

## Phase 2 — Features (parallel)

### Task 3: Build API endpoints
**Owner**: Developer-B
**Depends on**: Task 1, Task 2
**Spec**:
- Implement GET /posts, POST /posts, DELETE /posts endpoints
- Add request validation
- Test: `pytest tests/api/` must pass green

### Task 4: Add caching layer
**Owner**: Developer-A
**Depends on**: Task 3
**Spec**:
- Integrate Redis for session caching
- Add cache invalidation on data changes
- Test: `pytest tests/cache/` must pass green
```

**Format requirements:**
- Markdown headers: phase names, then task names
- Per-task fields: spec (required), owner/dependencies (optional)
- Spec is free-form; can include acceptance criteria, test commands, links, etc.
- Dependencies control task eligibility (a task can't start until its dependencies are approved and merged)

### Naming Conventions
- Task IDs are auto-derived from headers: `task-1`, `task-2`, etc., or use explicit IDs in the header
- Phase names are arbitrary ("Phase 1", "Sprint 1", "Setup", etc.)
- Owner hints: if a task specifies `**Owner**: Developer-A`, that developer is assigned it; otherwise tasks are split evenly

## Workflow: Linear History, Parallel Work

### Branch Naming
Each task gets its own branch:
- Developer-A: `dev-a/task-1`, `dev-a/task-3`, etc.
- Developer-B: `dev-b/task-2`, `dev-b/task-4`, etc.

### Worktrees (Default)
Each developer has a dedicated, persistent git worktree:
- `<project>-worktrees/dev-a/` — Developer-A's checkout
- `<project>-worktrees/dev-b/` — Developer-B's checkout
- `<project>/` — Lead's checkout (used only for merges)

**Benefit**: Developers can work in parallel without blocking each other. While Developer-B is finishing Task 2, Developer-A can already start Task 3 (after Task 1 is merged) in their own worktree.

### Rebase-Only Workflow (No Merge Commits)
The workflow enforces a **linear history** with no merge commits:

1. **On task assignment**: developer fetches, checks out main, then creates their task branch
2. **While working**: if main moves (another task merged), developer rebases immediately:
   ```bash
   git fetch origin
   git rebase origin/main
   ```
   Resolves conflicts, re-runs tests, then continues
3. **Before review**: final rebase + final test run
4. **On approval**: Lead merges with `git merge --ff-only` (fast-forward only)
5. **Result**: every commit in main is a buildable, coherent step; no hidden "merge" commits

### Parallel Execution Example
```
main ──●── (task 1 merged, base moved)
        \
         ●  dev-a/task-2 checks out, rebases onto new main, continues
        \ \
         \ ●  dev-b/task-3 also checks out in their worktree, works independently
          \ \
           ●─●──  both finish, get reviewed in parallel, merged in order

main ──●──●────●  (linear history)
```

## Output: progress.md Checkpoint

The skill creates a `progress.md` file (colocated with tasks.md) to track resumability:

```markdown
# Progress

Base branch: main
Tasks file: tasks.md
Worktrees: true

## Done
- task-1 ✅ (APPROVED, merged)

## In Progress
- task-2 🔄 (awaiting review) [branch: dev-a/task-2]

## Pending
- task-3
- task-4
```

If your session is interrupted, run the skill again with the same `tasks.md` — it will **resume from the checkpoint**, re-spawn teammates, and continue from where it left off.

## Review Checklist

The Reviewer applies this checklist per task:

- **Branch hygiene**:
  - Is the branch rebased onto main (no merge commits)? ✓
  - Are commits atomic and coherent (not one giant commit, not broken steps)? ✓
  - Branch name matches `dev-a/<task-id>` or `dev-b/<task-id>`? ✓

- **Correctness**: Does the code implement the spec correctly?
- **Tests**: Do all tests pass? Are new tests added where appropriate?
- **Style**: Does it follow project conventions (from CLAUDE.md or tasks.md)?

**Verdict**:
- **✅ APPROVED** → Lead merges to main
- **❌ CHANGES REQUESTED** → Reviewer lists specific issues; developer fixes and resubmits

## Examples

### Simple linear flow
```bash
/gtools:team-lead tasks.md

# Phase 1 (all sequential):
# Task 1 → approved → merged → Task 2 assigned → approved → merged → Task 3 assigned → ...
```

### Parallel execution
```bash
/gtools:team-lead tasks.md

# Phase 1: Task 1 (Developer-A) + Task 2 (Developer-B) run in parallel
# → Task 1 finishes first → approved → merged
# → Task 2 still working, rebases onto updated main (with Task 1's commits)
# → Task 2 finishes → approved → merged
# → Phase 2 tasks now eligible, assigned to developers in parallel
```

### Interrupted session
```bash
# First run
/gtools:team-lead tasks.md
# → Completes Task 1, Task 2 is in progress and unfinished

# Session interrupted, reconnect later
/gtools:team-lead tasks.md
# → Resumes: re-spawns teammates, continues Task 2 on the same branch
# → progress.md shows what was done, what's pending
```

### Without worktrees (shared checkout)
```bash
/gtools:team-lead tasks.md no-worktrees
# → Both developers share the project's working directory
# → Only one can have a branch checked out at a time
# → Lead serializes git commands to avoid collisions
# → Slower, but uses same disk space as a normal checkout
```

## Important Notes

### Linear History is Non-Negotiable
The workflow **never uses `git merge --no-ff` or manual merges**. Every merge is `--ff-only` and fast-forwardable. This ensures:
- Every commit on main is meaningful and independently testable
- No "merge commits" obscure the actual work
- `git log --oneline main` is clean and readable

### Rebase = Re-test
Whenever a developer rebases (because main moved), they **must re-run tests after rebasing**. The skill requires this before approving a task. This catches subtle issues where a sibling task's changes interacted with yours.

### No Force-Push to Main
The skill never force-pushes main. All merges are ff-only, so if an ff-only merge fails (main moved since approval), the developer rebases and resubmits — no history rewriting.

### Merge Serialization
Only one merge to main happens at a time. If both developers finish around the same time:
1. First approval → merged immediately
2. Second approval → queued until first merge completes
3. Then second developer's branch is rebased onto the new main tip and merged

This prevents race conditions and keeps history linear.

### Agent Teams Requirement
This skill requires Claude Code's Agent Teams feature:
```bash
# Enable when starting Claude Code
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude --teammate-mode auto
```

Without it, the skill will error early and ask you to enable Agent Teams.

## Troubleshooting

### "Base branch moved — rebase required"
The Reviewer rejected your task saying the branch is stale. Main advanced while you were working. Rebase onto main and re-run tests:
```bash
git fetch origin
git rebase origin/main
# Re-run your test command
```
Then message the Lead "TASK DONE" again (developer does this as part of their workflow).

### "No teams available" / Agent Teams error
Ensure you started Claude Code with Agent Teams enabled:
```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude --teammate-mode auto
```
Then restart and try again.

### Worktree conflicts
If you're using `no-worktrees` mode and get "another process is using this directory", the Lead is mid-merge. Wait for the Lead to finish, then retry.

### "Session interrupted mid-task"
Run `/gtools:team-lead tasks.md` again. It will:
1. Read `progress.md` to see what was done
2. Re-spawn teammates
3. Resume the in-progress task from its branch
4. Continue from there

All uncommitted work on the branch is preserved.

## Advanced: Custom Conventions

The skill derives coding standards, testing frameworks, and conventions from:
1. **tasks.md**: if it specifies "All code must pass `eslint`" or "Use pytest", the skill includes those
2. **CLAUDE.md** in the project root: project-wide conventions
3. **Default**: if neither source specifies, the skill asks you before spawning

You can customize this by:
- Adding a "## Development Standards" section to your tasks.md
- Creating a CLAUDE.md in your project with standards, testing framework, code style, etc.
